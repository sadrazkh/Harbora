# ۱۳ — رهگیری خطا (Sentry / GlitchTip)

اپ شما کرش می‌کند و تنها ردی که می‌ماند همان چیزی است که به لاگ کانتینر رسیده — که با هر ری‌استارت
از دست می‌رود. **رهگیری خطا** یعنی این استثناها را از خودِ کد جمع کنید و جایی نگهشان دارید که با
stack trace، تعداد رخداد و کاربر/درخواستِ مرتبط قابل جستجو باشد.

Harbora **خودش این را نمی‌سازد** — بازار این حوزه یکپارچه‌سازی می‌کند، نه از صفر می‌سازد، و همین
مسیر را این پلتفرم هم می‌رود: یک قالب یک‌کلیکی (**Sentry** در فهرست قالب‌ها، دسته‌بندی «رصد») که
یک سرور سازگار با پروتکل Sentry را self-host می‌کند، و صفحهٔ **رهگیری خطا** که همان DSN — از این
سرور، یا از هر سرور دیگری، حتی Sentry SaaS — را به‌صورت متغیر `SENTRY_DSN` به اپ‌های متصل تزریق
می‌کند.

> این فصل هم مثل ۱۰، ۱۱ و ۱۲ تصویر ندارد — همان دلیل: این جلسه به پنل در حال اجرا یا Docker دسترسی
> نداشت. مسیرها و برچسب‌ها از روی سورس پنل نوشته شده‌اند.

## قدم ۱ — استقرار سرور (یا استفاده از یکی که از قبل دارید)

اگر از قبل یک حساب Sentry SaaS یا یک سرور GlitchTip/Senty جای دیگری دارید، این قدم را رد کنید و
مستقیم به قدم ۲ بروید — DSN همان‌جا را کپی کنید.

برای self-host کردن روی همین Harbora:

۱. **قالب‌ها** › دنبال «Sentry» بگردید › **استقرار**.
۲. این قالب `postgres` و `redis` را در فهرست `requires` دارد، پس دو دیتابیس مدیریت‌شده هم به‌صورت
   خودکار برایش ساخته می‌شوند — با اعتبارنامهٔ تولیدشده، صورت‌حساب و چرخهٔ عمر خودشان، دقیقاً مثل هر
   دیتابیس مدیریت‌شدهٔ دیگر؛ کاری از دست شما نمی‌خواهد.
۳. **نام پروژه** و **نام برنامه** را بدهید، **ساخت و استقرار** را بزنید.
۴. وقتی اپ بالا آمد، یک‌بار به دامنهٔ خودش سر بزنید و از داخل رابط خودِ آن سرور یک سازمان (org) و
   یک پروژه بسازید. همان‌جا، زیر تنظیمات پروژه، **DSN** را می‌بینید — چیزی به شکل
   `https://<کلید>@<میزبان>/<شناسهٔ‌پروژه>`.

## قدم ۲ — ثبت DSN در Harbora

۱. **رهگیری خطا** › فرم **ارائه‌دهندهٔ جدید**.
۲. **نام**: هرچه بخواهید — «GlitchTip production»، «Sentry SaaS».
۳. **DSN**: همان مقداری که در قدم ۱ کپی کردید.
۴. **ساخت ارائه‌دهنده**. Harbora آن را رمزنگاری‌شده ذخیره می‌کند — نه یک مقدار ساختگی، چون Harbora
   نمی‌تواند کلید یک پروژهٔ واقعی را حدس بزند.

## قدم ۳ — اتصال به اپ

از همان صفحهٔ **رهگیری خطا**، زیر هر ارائه‌دهنده یک فرم **اتصال** هست: اپ را از فهرست انتخاب کنید.
از این لحظه، `SENTRY_DSN` روی صفحهٔ **متغیرهای محیطی** همان اپ دیده می‌شود — با برچسبی که می‌گوید
از کدام ارائه‌دهنده آمده — و با اولین **استقرار بعدی** آن اپ، واقعاً وارد کانتینرش می‌شود؛ تا آن
لحظه، «با استقرار بعدی اعمال می‌شود» را کنارش می‌بینید.

**اگر اپ از قبل خودش `SENTRY_DSN` دارد** — چون به یک حساب Sentry دیگر، مال خودتان، وصل است —
Harbora هیچ‌وقت آن را بازنویسی نمی‌کند. مقدار خودِ اپ همیشه برنده است، دقیقاً همان قاعده‌ای که برای
یک باکت یا ارائه‌دهندهٔ SMTP متصل هم برقرار است.

## قدم ۴ — هر runtime، طبق SDK رسمی خودش

`SENTRY_DSN` نامی نیست که Harbora اختراع کرده باشد — هر SDK رسمی Sentry، در هر زبان، دقیقاً همین
نام را به‌صورت پیش‌فرض می‌خواند وقتی چیزی صریح به آن داده نشود. یعنی معمولاً کافی است این متغیر
باشد و SDK را با تنظیمات پیش‌فرض init کنید.

### Node.js / TypeScript

```bash
npm install @sentry/node
```

```js
// server.js — قبل از هر import دیگری
import * as Sentry from "@sentry/node";

Sentry.init({
  // صریح نوشتنش اختیاری است — SDK به‌صورت پیش‌فرض همین متغیر را می‌خواند — اما نوشتنش یعنی
  // نبودِ آن یک خطای واضح موقع استارت می‌دهد، نه یک اپ ساکت بدون رهگیری.
  dsn: process.env.SENTRY_DSN,
});
```

### Python

```bash
pip install sentry-sdk
```

```python
import sentry_sdk

sentry_sdk.init(
    dsn=os.environ.get("SENTRY_DSN"),
    traces_sample_rate=0,  # فقط خطا؛ ردیابی کارایی جداست و هزینهٔ رویداد بیشتری دارد
)
```

### .NET

```bash
dotnet add package Sentry.AspNetCore
```

```csharp
// Program.cs
builder.WebHost.UseSentry(o =>
{
    // بدون Dsn صریح هم کار می‌کند — SDK رسمی .NET همین SENTRY_DSN محیطی را خودش می‌خواند —
    // اما مثل نمونهٔ Node، صریح نوشتنش یک خطای واضح موقع استارت می‌دهد به‌جای سکوت.
    o.Dsn = Environment.GetEnvironmentVariable("SENTRY_DSN");
});
```

### هر runtime دیگر

فهرست کامل SDKهای رسمی (Go، PHP، Ruby، Java/Kotlin، Rust، …) در
[`docs.sentry.io/platforms`](https://docs.sentry.io/platforms/) است — همه از یک قرارداد پیروی
می‌کنند: یک تابع/متد `init` که یک DSN می‌گیرد، و اکثرشان اگر چیزی صریح داده نشود همین
`SENTRY_DSN` محیطی را خودشان می‌خوانند. GlitchTip دقیقاً همان API سرور Sentry را پیاده‌سازی کرده،
پس هر SDK رسمی Sentry بدون تغییر با آن هم کار می‌کند.

## جدا کردن

از همان صفحهٔ **رهگیری خطا**، دکمهٔ ✕ کنار نام اپ در فهرست «اپ‌های متصل». کانتینر در حال اجرا تا
استقرار بعدی هنوز `SENTRY_DSN` قبلی را دارد — env هیچ‌وقت داخل ایمیج پخته نمی‌شود، پس هر استقرار
بعدی، هرچه در آن لحظه صفحه نشان می‌دهد را واقعاً می‌سازد، چه استقرار معمولی باشد چه rollback.

حذف کامل یک ارائه‌دهنده، تا وقتی به اپی متصل است، رد می‌شود و نام همان اپ(ها) را می‌گوید — باید
اول از همه‌شان جدا شود.
