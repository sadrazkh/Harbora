# Round Three — "deploy a Python bot without fear", plus the small open backlog

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:subagent-driven-development.

**Goal:** Make the path from "I have a Python Telegram bot in a repo" to "it is running and I can
see that it is running" short, automatic and documented — and close the small open backlog items
that need no Docker and no live host.

**Baseline at start:** master `e1b69e0`, 6694 tests green (6162 Harbora.Tests · 517 NodeAgent ·
15 NodeIngress).

## Global Constraints

- Commits carry the owner's name alone. No `Co-Authored-By` trailer.
  `git -c user.name="sadra zadeh khameneh" -c user.email="1986.aandrii@gmail.com" commit`
- `MSBUILDDISABLENODEREUSE=1` and `-p:UseSharedCompilation=false` on every build. Agents work in
  sibling worktrees and MSBuild's reused node servers cross-contaminate them with no error.
- Never run `npm run build` while `dotnet test` is running. Vite rewrites the hashed assets
  mid-flight, `Harbora.Web` fails to build, and **`Harbora.Tests` then does not run at all** while
  three small green `Passed!` lines still print.
- Capture the exit code before piping: `dotnet test Harbora.slnx --nologo -v q > /tmp/t.log 2>&1;
  echo "EXIT=$?"`. Then confirm a `Harbora.Tests.dll` line is present in the log.
- Zero new compiler warnings.
- No security review, no attack scenarios, no vulnerability hunting. Out of scope this round.
- Nothing payment-gateway. Nothing Iranian-market (Modian, `.ir`, edge cache).
- No new capability may be reported working on evidence this machine cannot produce. There is no
  Docker here and no live Postgres credentials. A test that needs either is written and marked for
  the CI lane, and the report says plainly that it was not observed locally.

## The finding this round is built on

`ServiceKind.Worker` is fully wired: `ServicePlan` already suppresses the domain, the public route
and the HTTP health check, and `DeploymentPipeline` honours all three. The Telegram template
already exists and already sets `"kind":"worker"`. None of that needs building.

What is missing is everything downstream of "and now run my Python file":

1. `Buildpacks.Python` picks an entry from `app.py, main.py, wsgi.py, server.py, manage.py` and
   **falls back to `app.py` when none of them exists**. A Telegram bot is almost always `bot.py`.
   The generated image is then `CMD ["python","app.py"]` against a file that is not there.
2. The container's restart policy is `UnlessStopped`, so that image crash-loops rather than
   stopping — the app reads as running.
3. `PYTHONUNBUFFERED` is not set, so a bot that *is* working prints nothing into the log for as
   long as its buffer takes to fill. There is no way to tell case 2 from case 3 from the panel.
4. The deploy log says `auto-detected Python` and never says which file it chose.
5. `App.Command` is cron-only. A Worker has no start-command field anywhere, so there is no way to
   correct a wrong guess without adding a Dockerfile.

That is this repo's defining defect class, three times over in one code path.

## Wave 1

### P1 — The Python buildpack runs the right file, or says it cannot find one

**Files:** `src/Harbora.Infrastructure/Deployments/Buildpacks.cs`,
`src/Harbora.Infrastructure/Deployments/DeploymentPipeline.cs` (the detection log line),
`tests/Harbora.Tests/BuildpackTests.cs`.

- Entry candidates gain `bot.py`, `run.py`, `__main__.py`, `start.py`. Existing names keep their
  current precedence so nothing already deploying changes behaviour.
- **The silent fallback goes.** When no candidate exists, detection returns null and the deploy
  fails with a sentence naming what was looked for. An image that cannot start must not be built.
- `manage.py` leaves the candidate list. `python manage.py` with no arguments prints usage and
  exits — a Django repo detected this way starts, exits, and restarts for ever.
- `ENV PYTHONUNBUFFERED=1` on the generated image.
- Non-HTTP kinds (`Worker`, `Cron`, `ReleaseTask`) get no `EXPOSE` and no `PORT`.
- The deploy log names the entry: `auto-detected Python (entry: bot.py)`.

### P2 — A start command for services that have no Dockerfile

**Files:** `src/Harbora.Domain/Apps/App.cs`, a migration, `src/Harbora.Web/Views/Apps/`,
`src/Harbora.Web/Controllers/AppsController.cs`, `Buildpacks.cs` consumption, tests.

`App.Command` is documented and wired for `Cron` only. Give a buildpack-built app of any kind an
explicit start command that overrides the detected one, so a wrong guess is correctable from the
panel in one field instead of by committing a Dockerfile.

## Landing procedure per branch

1. Read the agent's report in `.superpowers/sdd/r3/`.
2. `git rebase master` in its worktree. A clean git merge is not the absence of a semantic
   conflict — build after every rebase.
3. Full suite, exit code captured, `Harbora.Tests.dll` line confirmed present.
4. Migrations: build first, then confirm `MigrationConsistencyTests` passes. A migration scaffolded
   against a stale assembly captures the old model.
5. Merge, then re-run the full suite on master before the next merge.
